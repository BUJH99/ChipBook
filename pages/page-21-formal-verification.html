21-1. 검증 기법 선택

Emulation과 FPGA prototype은 더 긴 software/system scenario를 실행하는 데 사용할 수 있다. 도구 이름보다 질문과 관측 범위에 맞게 선택한다.

계산·동작 예

FIFO overflow 금지 같은 local property와 긴 OS boot scenario는 필요한 검증 방법과 비용이 다르다. 서로의 공백을 메우도록 조합한다.

한 방법의 통과 결과를 다른 방법이 다루는 현상까지 확장해 해석하지 않는다.

각 결과가 보장하는 범위와 비용을 설명한다.

21-2. Property와 환경 가정

Clock와 reset 의미를 property와 맞춰야 한다. 과도한 assumption은 반례를 없애면서 실제 동작도 제거할 수 있다.

계산·동작 예

Ready가 영원히 낮아도 된다는 환경에서 모든 요청이 반드시 완료된다고 증명하려 하면 liveness 조건이 맞지 않는다. 필요한 fairness를 명시하고 그 가정이 실제 환경에서 성립하는지 확인한다.

코드와 동작

// One-cycle request acknowledgement in the chosen synchronous interface.
property p_request_ack;
    @(posedge iClk) disable iff (!iRstn)
        iReq |=> oAck;
endproperty
assert_request_ack: assert property (p_request_ack);
cover_request: cover property (@(posedge iClk) disable iff (!iRstn) iReq);
// A proof with an unreachable iReq can be vacuous; inspect assumptions and cover.

DUT가 보장해야 할 동작을 assume으로 넣어 검사를 순환 논리로 만들지 않는다.

잘못된 가정이 실제 버그를 숨기는 사례를 찾는다.

21-3. Formal 실행과 해석

Counterexample은 실패를 재현하는 상태·입력의 sequence다. Inconclusive는 통과나 실패가 아니라 분석이 결론에 도달하지 못한 상태다.

계산·동작 예

Depth 20까지 overflow가 없었다는 결과는 21 cycle 이후의 오류 가능성을 배제하지 않는다. 어떤 상태에서 검사를 시작했는지도 결과와 함께 기록한다.

Timeout이나 depth 제한 종료를 PASS로 보고하지 않는다.

bounded 통과와 무제한 증명을 구별한다.

21-4. 분할과 추상화

Cone of influence는 property에 영향을 주는 논리 범위를 좁히는 관점이다. Assume-guarantee에서는 한 부분의 보장이 다른 부분의 가정과 맞아야 한다.

계산·동작 예

큰 memory를 추상 model로 바꾸면 data 보존·주소 alias·read/write 순서 중 어떤 성질을 유지했는지 기록한다. 원래 설계에 없는 동작을 허용하는지도 확인한다.

작아진 모델에서 증명이 쉬워졌다는 것만으로 원래 설계의 모든 성질을 검증했다고 하지 않는다.

줄인 모델의 가정과 누락 행동을 기록한다.

21-5. Equivalence와 ECO 검증

Register retiming이나 encoding 변경은 단순 node matching을 넘어서는 대응이 필요할 수 있다. ECO 뒤에는 변경 범위뿐 아니라 주변 영향도 확인한다.

계산·동작 예

기능 ECO가 아닌 timing ECO에서 동일 입력·초기 상태의 결과를 비교한다. Black box와 unmatched point가 결과를 얼마나 제한하는지 함께 읽는다.

코드와 동작

// Example comparison point; reset/initial-state relation is part of the proof.
assert_same_output: assert property (
    @(posedge iClk) disable iff (!iRstn)
    RefValid && ImplValid |-> RefData == ImplData
);
// This checker alone is not a complete sequential-equivalence proof.

이름이 같은 register가 반드시 같은 의미의 상태라고 가정하지 않는다.

동치 검사의 전제와 실패 원인을 설명한다.

21-6. 검증 완료와 추적성

Code/functional coverage, property 결과, bug와 waiver는 서로 다른 정보를 준다. Regression의 재현성·seed·tool·revision을 보존한다.

계산·동작 예

Coverage hole이 unreachable인지, stimulus 부족인지, checker 문제인지 분류한다. Waiver에는 타당성·영향·재검토 조건을 남긴다.

Coverage percentage 하나만으로 모든 중요한 corner가 검증되었다고 결론 내리지 않는다.

숫자 하나 대신 근거로 미검증 위험을 설명한다.
