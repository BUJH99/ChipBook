Part 24

하드웨어 보안과 기능 안전

24-1. 위협과 고장 모델

Safety fault model은 우발 고장이 시스템에 주는 영향을 다룬다. 같은 오류 검출 장치도 어떤 가정에서 어떤 실패를 줄이는지 명시해야 한다.

계산·동작 예

외부 debug 접근, DMA와 boot 경로를 자산 지도에 표시하고 각각 필요한 권한을 정의한다. 우발 bit flip과 의도적 명령 변조는 다른 시험 목적을 갖는다.

보안 공격과 우발 고장을 한 failure rate로 섞지 않는다.

의도적 공격과 우발 고장을 구별한다.

24-2. Root of Trust와 Secure Boot

Secure boot는 다음 단계의 코드와 필요한 metadata를 검증하고 실패 시의 동작을 정의한다. Key 저장, lifecycle, rollback 방지와 debug 정책이 함께 설계되어야 한다.

계산·동작 예

서명 확인을 통과한 오래된 image라도 알려진 문제를 가진 version으로 돌아가면 보호 목표를 깨뜨릴 수 있어 version 정책을 검토한다.

암호 알고리즘을 썼다는 사실만으로 key 관리와 boot chain 전체가 안전하다고 결론 내리지 않는다.

검증되지 않은 코드로 이어지는 경로를 찾는다.

24-3. 격리와 접근 제어

CPU privilege와 memory protection, DMA/IOMMU와 bus firewall의 경계를 함께 확인한다. 기본 거부와 오류 응답, side effect 여부를 정의한다.

계산·동작 예

CPU가 접근할 수 없는 secure buffer를 DMA가 읽을 수 없는지 같은 정책으로 시험한다. 실패한 write가 상태를 일부 바꾸는지도 확인한다.

소프트웨어 pointer 검사만으로 다른 bus master의 접근을 통제할 수 있다고 생각하지 않는다.

CPU와 DMA의 접근 경계를 함께 검사한다.

24-4. Debug와 물리적 공격 방어

Fault injection과 side-channel 분석은 설계의 방어 가정을 점검하는 방법이다. 보호 기능은 정상 debug·제조·복구 절차와도 일관되어야 한다.

계산·동작 예

개발·제조·현장 mode에서 허용되는 debug register와 인증 조건을 비교한다. 잠금 이후에도 예외 경로가 권한을 우회하지 않는지 확인한다.

Debug를 전부 끄는 선택의 유지보수·장애 분석 영향도 고려한다.

방어의 가정과 검증 범위를 명시한다.

24-5. 고장 검출과 복구

검출 이후 알림·격리·재시도·복구·safe state의 책임도 정해야 한다. 중복 장치가 같은 원인으로 실패하는 common-cause 문제를 고려한다.

계산·동작 예

두 core가 같은 잘못된 입력과 같은 설계 결함을 공유하면 lockstep 비교가 차이를 찾지 못할 수 있다. 독립성 가정과 검출 범위를 문서화한다.

Redundancy가 있다는 이유만으로 모든 고장에 강하다고 표현하지 않는다.

검출 범위와 공통 원인 고장을 구별한다.

24-6. 증거와 시스템 검토

적용 표준의 범위와 제품 맥락, 책임과 잔여 위험을 명시한다. 교육 예제의 mechanism demonstration은 제품 인증 결과와 구분한다.

계산·동작 예

요구 → 보호 mechanism → 시험 → 결과 → 남은 조건의 대응표를 만든다. 변경 시 영향을 받는 증거를 다시 검토한다.

표준 이름을 나열하거나 checklist를 채운 것만으로 인증을 주장하지 않는다.

교육 예제를 제품 인증 결과로 표현하지 않는다.
