25-1. 개발 환경과 재현성

Source와 generated output, 임시 로그를 분리하면 변경 원인을 추적하기 쉽다. Version control은 결과뿐 아니라 의도와 검증 근거를 함께 남기는 도구다.

계산·동작 예

새 checkout에서 동일 build/test 명령으로 결과를 만들고 누락된 dependency를 확인한다. 실행 중 얻은 큰 산출물은 source와 구분해 관리한다.

개인 machine의 숨은 PATH나 작업 directory에 의존하는 script를 그대로 공유하지 않는다.

사용 도구와 입력 버전을 기록한다.

25-2. 스크립트와 데이터 처리

Script는 입력 검증, exit status와 결과 파일 경로를 명시해야 한다. 구조화된 결과를 사용하면 log의 우연한 문구 변화에 덜 취약하다.

계산·동작 예

여러 corner의 timing summary를 읽어 mode·corner·slack·unconstrained count를 표로 만든다. 누락된 run을 0 violation으로 처리하지 않고 별도 실패로 표시한다.

코드와 동작

import csv
from pathlib import Path

rows = list(csv.DictReader(Path('timing.csv').open()))
required = {'mode', 'corner', 'slack_ns', 'status'}
assert rows and required <= rows[0].keys()
for row in rows:
    if row['status'] != 'complete':
        raise RuntimeError(f"Incomplete run: {row['mode']} / {row['corner']}")
    slack = float(row['slack_ns'])
    print(row['mode'], row['corner'], 'PASS' if slack >= 0 else 'VIOLATION', slack)

실행 명령이 끝났다는 사실과 필요한 산출물이 정상 생성됐다는 사실을 구별한다.

입력과 결과를 반복 생성하고 실패를 감지한다.

25-3. Simulation과 Debug

Seed와 입력, model·tool version을 보존해야 같은 실패를 재현할 수 있다. 파형은 시간 단위와 X/Z, event 순서를 함께 읽는다.

계산·동작 예

최초 error와 관련 scope를 찾은 뒤 해당 입력 sequence를 줄여 최소 재현을 만든다. 최종 timeout 메시지만 보는 것보다 앞선 protocol 위반을 찾는 것이 중요하다.

코드와 동작

# 예제: 도구와 언어 지원에 맞게 파일 목록을 지정
iverilog -g2012 -s tb_top -o sim.out rtl.sv tb.sv
vvp sim.out
# log의 exit code와 PASS/FAIL, waveform을 함께 확인

Waveform에 보이는 마지막 증상을 원인으로 단정하지 않는다.

실패를 최소 입력으로 재현한다.

25-4. 오픈 도구로 RTL부터 Layout까지

각 도구의 지원 범위와 PDK 상태를 확인한다. 교육용 flow의 성공은 제조용 signoff와 구분해 해석한다.

계산·동작 예

Yosys의 netlist와 OpenROAD의 physical 결과를 같은 top·library·constraint로 연결한다. 단계 사이의 파일 revision과 단위가 맞는지 확인한다.

코드와 동작

# OpenROAD Flow Scripts: use an installed, revision-pinned flow and platform.
# DESIGN_CONFIG supplies the top, RTL, SDC and platform settings.
make DESIGN_CONFIG=./designs/<platform>/<design>/config.mk
# Inspect synthesis, placement, CTS, routing and timing reports separately.
# A successful educational flow is not a foundry signoff approval.

명령이 exit 0이라는 것만으로 DRC·timing·power와 제조 인계가 모두 완료됐다고 보지 않는다.

교육용 flow와 제조용 signoff의 범위를 구분한다.

25-5. FPGA 구조와 구현

같은 RTL도 ASIC standard cell과 다른 resource로 mapping된다. Clocking, memory inference, pin과 IO standard 및 timing constraint를 확인한다.

계산·동작 예

Multiplier를 DSP에 mapping하는 경우와 LUT logic으로 구현하는 경우의 resource·timing을 비교한다. 단순 gate count 비교로 ASIC 결과를 예측하지 않는다.

RTL 시뮬레이션 통과만으로 board pin과 clock constraint가 올바르다고 가정하지 않는다.

ASIC과 FPGA의 구현 차이를 설명한다.

25-6. 보드 실습과 Prototype

On-chip analyzer는 선택한 내부 신호를 관측하지만 sampling clock와 trigger 범위가 제한된다. Prototype의 기능·속도 범위를 명시한다.

계산·동작 예

UART echo 실습에서 내부 TX state, 실제 pin waveform, host 수신 byte를 연결한다. Baud 설정이 맞아도 pin mux나 전압이 다르면 통신이 실패할 수 있다.

실제 board 정보 없이 pin constraint와 전압 값을 임의로 적용하지 않는다.

bitstream 생성부터 관측 결과까지 재현한다.

25-7. 자동 회귀와 결과 관리

결과 diff는 같은 조건의 metric을 비교하고 missing result를 구분한다. Artifacts에는 재현에 필요한 로그·파형·설정이 포함된다.

계산·동작 예

실패한 seed를 다음 run에서 고정해 재현한 뒤 수정 전후를 비교한다. Timeout·compile error·mismatch를 다른 failure class로 분류한다.

Fail을 ignore하거나 retry 성공만 남겨 불안정성을 감추지 않는다.

실패를 숨기지 않고 재실행 방법을 남긴다.
